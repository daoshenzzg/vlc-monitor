# VLC 监播工具：稳定性修复与任务拆分计划

日期：2026-10-16  
状态：已在独立项目实施，离线与本地受控验收通过；不代表真实微信、Windows 或长期值守已验收。见 [实施记录](2026-10-16-implementation.md)。

## 1. 目标与范围

依据关联审查会话 `01a143dc-5203-7ac1-9043-200e8961930f`，修复 5 项已定位问题：VLC 回调失败状态不一致、取帧时钟竞争、微信队列丢消息、SQLite 阻塞界面、VLC 重复装载资源累积。

微信按用户最新要求收敛为：**同一次异常只关注首次告警与正常恢复，中间重复直接丢弃，不靠周期消息维持关注度。** 此要求优先于旧实施计划中“可选微信重复提醒”的设计。

本计划不改变：检测阈值、ROI 几何、异常确认/恢复判定、本地声音与前台提醒、微信登录绑定和凭证保护、一个源一个播放器的架构。停止监播、切源、编辑区域、退出等仍不是“恢复正常”。

不在本轮追加：持久化微信发件箱、跨重启补发、自动重连守护、多源监播、算法重写或全面性能优化。

## 3. 微信发送契约

### 3.1 已确定的产品规则

1. 去重以一次异常事件为单位，沿用 `(session_id, run_id, event.id)`，不能用区域名或消息文本去重。恢复后再次异常是新事件，应有新的首次告警。
2. 同一事件重复 `start` 不创建第二条首次任务；持续 `update` 在微信入口直接丢弃，不入发送队列、不累积待发消息、不逐条写“已丢弃”历史。
3. 移除微信周期 `repeat` 调度以及设置中的重复提醒开关、间隔控件。不能仅默认关闭而允许旧配置重新启用。
4. 正常恢复最多创建一个恢复任务；重复 `end` 不重复发送。只有 `end_reason == "恢复正常"` 才是恢复通知。
5. 本地确认、静音、周期声音等逻辑保持不变。微信去重不能删掉检测事件、活动状态或本地历史更新。
6. 保留 session/run、区域 revision、generation/send_epoch 隔离；关闭、解绑、切换运行后旧请求的迟到回执不得污染新运行。

### 3.2 建议采用的边界默认值

以下是供本次计划评审确认的实施默认值，尚未实现。

| 场景 | 计划行为 |
| --- | --- |
| 首次已被接口接受，异常持续很久 | 不再发送任何中间提醒；只等真正恢复 |
| 首次还在聚合窗口且一次也未尝试，就恢复 | 保留现有短暂异常合并：发送一条“首次异常，现已恢复正常”，同时表达两个状态，不连发两条 |
| 首次已开始发送，期间恢复 | 保留恢复任务；首次在有限重试预算内结束后，再发送恢复，保持同事件顺序 |
| 首次明确失败、过期或因容量被拒绝，但事件状态仍被跟踪，随后正常恢复 | 恢复独立有一次发送机会，不再因 `initial == failed` 直接取消；文案提示“首次告警未确认发送成功” |
| 首次结果不确定，随后恢复 | 正常发送恢复，并保留首次结果不确定提示，不能声称用户此前已收到 |
| 没见过首次事件，只收到孤立恢复/旧运行结束事件 | 不凭空生成通知；保持上下文校验。不能为补发恢复而绕过运行隔离 |
| 手动停止、编辑、切源、退出导致事件结束 | 取消待发内容，不伪造恢复；已交给接口的请求不能保证撤回 |
| 正常恢复后再次出现异常 | 按新事件发送首次；不在本轮额外引入跨事件抖动压制，以免漏掉真实新异常 |

### 3.3 重复消息与失败重试必须分开

- 丢弃的是业务层中间重复提醒，不是无条件丢弃首次/恢复的失败结果。
- 建议保留现有有限重试：每个首次或恢复任务最多 **3 次总尝试**，退避 **2 秒、8 秒**，尊重服务端更长的 `Retry-After`；TTL 仍为 **300 秒**，重试不能重置 TTL。
- 只对现有 `transient`、`uncertain` 分类有限重试；明确失败和会话失效不无限重试。重复事件输入不能重置尝试次数，也不能生成新的重试任务。
- 重试复用原 `client_id`，但不能假定服务端据此实现幂等。超时后重试仍可能产生少量重复，这与无限周期提醒不同。
- `accepted` 只表示接口接受，不是手机送达或已读。“首次收到、恢复收到”是实机验收目标，不是本地队列能绝对保证的承诺。

### 3.4 容量与拥塞处理

- 保留已有发送队列 100 条、单批最多 8 个事件、文本上限 1800、聚合窗口 2 秒及单请求在途约束，不通过无界扩容解决问题。
- 微信入口邮箱先过滤 `update`，再按同事件、同阶段合并。结束控制仍需可靠传递，用于取消非正常结束和识别恢复；不能因为去掉 repeat 就删掉 end 通道。
- `_enqueue` 不再需要“淘汰 repeat 腾位”分支；新任务变量与所有遍历变量分离，队列拒绝必须指向正确事件和阶段，首次被拒后不能永远卡在 pending。
- 全部容量均被不同事件的首次/恢复占满时，仍可能拒绝新任务。保留有界行为，明确报告 `queue_full` 及未发送状态；不得悄悄挤掉已排队的首次/恢复，也不得谎报成功。
- 同时验收入口邮箱和发送队列两层溢出；入口控制溢出的安全取消策略必须有可见状态，不能只验证最终队列长度。
- 该设计防的是同一次持续异常反复通知，不承诺所有独立事件同时爆发时全部送达；不为了“绝对不丢”增加无限积压或重启补发风暴。

### T1：修复 VLC 格式回调失败边界（R1，第一优先）

修改范围：`src/vlc_monitor/playback/vlc_backend.py`；新增专用 `tests/test_vlc_backend.py`。

- 在局部变量完成尺寸检查、容量计算、32 字节对齐的分配与视图构造，全部成功后在锁内统一提交 `_allocation`、`_storage`、`_shape`。
- 格式回调失败不能让 Python 异常穿过 ctypes 边界，明确返回 0；失败不能留下新尺寸与旧缓冲区混用的状态，也不能提前释放原有存储。
- 保留播放器停止/释放后才释放回调和内存所有者的顺序；不得为避免等待而强杀线程或释放原生仍在使用的内存。
- 检查相邻回调的异常出口，特别是 `_display` 帧复制失败；如纳入防护，应跳过失败帧而非发布半成品，不能改变取帧有效性规则。

验收：首次分配失败、已有缓冲区后分配失败、正常分辨率切换、非法尺寸；使用真实 ctypes 回调包装故障注入，断言失败返回 0 和状态一致，不制造真实 OOM。补本地受控视频播放/停止冒烟，不能以 Python 测试代替原生集成验证。

### T2：修复取帧与检测时钟顺序（R2）

修改范围：`src/vlc_monitor/monitoring/controller.py`、`tests/test_controller.py`；必要时仅补 `tests/test_detection.py` 核心回归。

- 将本轮用于 `observe`、`tick`、`consume` 的单调时钟放到获取帧快照之后读取，核对首帧等待、宽高比中断及采样间隔也使用正确时点。
- 保留真正未来时间戳、旧帧、跨会话帧和长时间调度中断的拒绝规则，不通过放宽校验掩盖竞争。

验收：取帧过程中时钟推进 1ms，合法黑屏连续计数仍达到阈值；真正未来帧仍被拒绝；无新帧超时、首次连接超时、冻结基线、恢复与运行切换不回归。

### T3：微信只发首次与恢复，并修复丢消息（R3）

修改范围：`notifications/wechat_queue.py`、`notifications/wechat_service.py`、`ui/wechat_settings.py` 及其专用测试。以下路径均在 `src/vlc_monitor/` 下；共享配置与主窗口由 T6 统一集成。

- 先在 `publish` 入口过滤持续 update，再在队列防御性忽略；保留同阶段去重和原始创建时间。
- 删除周期 repeat 的创建、截止时间和淘汰逻辑，修复 `_enqueue` 新旧 entry 混用及报告身份错误。
- 落实第 3 节首次/恢复状态转换，包括首发失败不阻断恢复、短暂异常合并、重复结束幂等及有限重试。
- 删除微信重复设置控件及配置回传；同步修改 service 的配置入口，避免任何旧调用重新开启 repeat。
- 保留网络来源限制、凭证库、登录绑定、测试消息和关闭默认零网络行为。不改传输协议，不扩大主机白名单。
- 过载/取消/失败状态要能到达现有 UI 与历史；重复丢弃无需逐条记录，避免把消息风暴变成存储风暴。

验收重点：

1. 同事件重复 start、上万次 update、跨多个旧重复周期的 tick，最终只有一个首次任务和一个正常恢复任务；短暂异常按合并规则只有一条。
2. 在途恢复、首发失败/过期/不确定后恢复、重复 end、非正常结束、恢复后新事件均符合契约。
3. 两层满队列均验证实际成员、event_ids、phase 和状态，不只检查长度；满队列绝不把拒绝记到无关旧事件。
4. 首次/恢复的重试不超过 3 次总尝试，TTL 和 client_id 不重置；旧 generation/run 迟到回执不影响新状态。
5. 微信关闭无网络；本地确认/静音不影响微信，本地持续提醒不被一并移除。

### T4：历史数据库移出界面线程（R4）

修改范围：`storage/event_store.py`，新增 `storage/event_service.py` 与专用测试；`ui/main_window.py` 和主窗口测试仅由 T6 修改。

方案边界：一个专用存储 worker 创建、使用并关闭 SQLite 连接。GUI 和检测线程都不操作该连接；不通过 `check_same_thread=False` 共享连接。

- 将初始化/建表、启动清理、recent、upsert、acknowledge、local/wechat delivery、定期清理与 close 全部移入存储线程，不只改本地通知写入。
- GUI 保持立即更新内存历史和提醒，只提交不可变快照。入口有界、合并唤醒，不能每条记录发一个无界 Qt 排队信号。
- 建议初始预算：入口最多 1024 条记录，每批最多 64 条；SQLite 锁等待 100ms，锁冲突最多重试一次，重试不增加入口总量。这里是待实测调整的初值，不是已验证容量结论。
- 一批写操作共享事务；同通知分组仍保留各自 sequence、attempts、时间。保持提交顺序，不能跨确认/清理屏障重排，不能用旧活动快照覆盖已结束事件。
- 队列按实际记录数计量，单命令也不能藏无限列表。过载或重试耗尽时显式标记未持久化，聚合提示“仅内存有效/部分历史未保存”，不阻断本地与微信告警。
- recent 异步回填按 id 合并，不能覆盖本次运行更晚的事件结束、确认或发送结果。禁止直接以旧查询结果替换 `self.history`。
- 退出先停生产者并接纳最后的事件/回执，再封闭入口，提交 flush/close 屏障，等存储关闭确认后退出。GUI 不同步 wait、不强杀线程。
- flush 超出有限预算应提示重试或明确放弃未保存数据，不能无限假死；即便放弃，也需等待存储线程安全关闭。播放器停止失败恢复运行时，存储不能被提前关死。

验收：临时数据库第二连接持写锁，连续提交多事件及确认/清理，GUI 心跳和操作仍响应；验证批量持久化、容量上限、磁盘错误、初始化失败、启动回填竞态、最后一刻回执、重复退出和播放器停止失败。UI 响应性能记录实测值，不把工作线程存在等同于界面不会阻塞。

### T5：缓存 VLC binding，限制重复加载（R5）

修改范围：`src/vlc_monitor/platform/vlc_locator.py`；新增专用 `tests/test_vlc_locator.py`，现有选择器交互不改。

- 按已规范化的 VLC location 缓存成功 binding；同路径后续直接复用，避免诊断和重连重复 CDLL/add_dll_directory。
- 换路径仍要求重启，不允许运行中替换已加载的 VLC。
- 装载过程串行化；仅在验证成功后发布成功缓存。失败清理本次可安全关闭的 DLL 搜索目录句柄，不把失败对象无限追加到全局列表。
- 不手工强制卸载可能已被 binding 引用的原生库；部分装载污染无法安全恢复时明确要求重启，而不是承诺完整回滚。

验收：同路径 100 次调用只做一次成功初始化，保留句柄数不随调用次数增长；不同路径仍拒绝；失败后重试/重启提示正确，Windows 搜索目录句柄释放、macOS core 加载路径通过 mock 检查。Windows 资源结论仍需实机补验。
